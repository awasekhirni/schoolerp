Database Documentation

--Domain: School Management System (SMS) / Multi-Tenant SAAS ERP
-- database Object 1: institutes.institutes
-- database Object Type: Table
-- Description: The `institutes` table serves as the foundational root entity for the entire multi-tenant architecture of the Halima Fathima Global School platform. It encapsulates the core identity, configuration, and operational parameters of each educational institution onboarded onto the SAAS platform. Every record represents a distinct school, college, or university, storing critical metadata such as the institution's official name, primary contact email, physical address, domain mapping for custom URLs, and platform type (Web or App). Furthermore, it tracks the lifecycle state of the institution through status flags, links to the owning user or administrator, and maintains references to the active UI theme. By acting as the primary tenant identifier, this table ensures strict data isolation across the system, allowing a single deployment to securely host thousands of independent educational entities while providing centralized SAAS-level oversight and subscription management.
-- Business Case: In a multi-tenant SAAS environment, the `institutes` table is the absolute cornerstone of data governance, security, and billing operations. Without this central registry, the platform would be unable to route requests to the correct tenant context, leading to catastrophic data leakage between schools. It enables the SAAS provider to enforce subscription limits, manage billing cycles via linked plans, and control feature access based on the institution's tier. From an operational standpoint, it allows the platform administrators to onboard new schools seamlessly, assign dedicated system admins, and monitor the health and activity of each tenant. Additionally, by storing domain and theme configurations, it empowers each institution to maintain its unique brand identity on the platform, which is critical for market adoption and user trust in the highly competitive EdTech sector.
-- KPIs: Tenant onboarding rate, active tenant ratio, subscription renewal rate, custom domain adoption rate, average tenant lifecycle.
-- Feature Reference: M01-F001, M01-F002, M01-F015, M16-F001

--Domain: School Management System (SMS) / Multi-Tenant SAAS ERP
-- database Object 2: institutes.branches
-- database Object Type: Table
-- Description: The `branches` table represents the physical or operational campuses associated with a primary institute within the multi-tenant architecture. While an institute represents the overarching educational brand or legal entity, a branch denotes a specific geographic location or administrative division where students are physically taught. This table stores essential branch-level metadata, including the branch name, operational status, and a foreign key linking it back to the parent institute. It is designed to support large educational networks, such as university systems or school chains, that operate multiple campuses under a single centralized management dashboard. By segregating data at the branch level, the platform ensures that academic routines, fee collections, and attendance records remain distinct for each campus, while still allowing the central institute administration to generate consolidated reports and enforce unified policies across all locations.
-- Business Case: The business necessity for the `branches` table arises from the operational reality of modern educational networks that manage multiple campuses. Without branch-level segregation, a school chain would face insurmountable challenges in tracking campus-specific performance, managing localized fee structures, or assigning campus-specific staff. This table enables decentralized administration with centralized oversight, allowing branch principals to manage daily operations while the central board monitors overall network health. Financially, it allows for precise revenue tracking per campus, enabling data-driven decisions about where to allocate resources, open new campuses, or optimize existing ones. Furthermore, it supports localized compliance and reporting requirements, ensuring that each branch can adhere to regional educational regulations while maintaining the overarching brand standards and operational efficiencies of the parent institute.
-- KPIs: Campus utilization rate, branch-level revenue contribution, inter-branch student migration rate, localized fee collection efficiency, branch operational cost ratio.
-- Feature Reference: M01-F003, M01-F004, M16-F002

--Domain: School Management System (SMS) / Multi-Tenant SAAS ERP
-- database Object 3: auth.users
-- database Object Type: Table
-- Description: The `users` table is the central authentication and identity management repository for all human actors interacting with the Halima Fathima Global School platform. It stores critical credential data, including hashed passwords, email addresses, phone numbers, and social media links, alongside profile metadata such as profile images and user types (e.g., Student, Teacher, Admin, Parent). The table enforces multi-tenancy by linking each user to a specific `institute_id` and `branch_id`, ensuring that user identities are scoped correctly within the SAAS architecture. It also tracks user engagement metrics like last active time, platform preference (Web or App), and device information. By serving as the single source of truth for authentication, this table integrates seamlessly with role-based access control (RBAC) systems to dictate exactly what resources and actions each individual can access across the entire ecosystem.
-- Business Case: The `users` table is the critical gateway to platform security, user experience, and operational efficiency. From a security perspective, it safeguards the platform against unauthorized access by managing secure credential storage and session tracking. For the business, it enables highly personalized user experiences; by knowing a user's role, platform preference, and last active time, the system can tailor dashboards, send targeted notifications, and optimize engagement strategies. In a SAAS model, accurate user tracking is also essential for billing, as many subscription plans are priced based on the number of active students or staff members. Additionally, by linking users to specific institutes and branches, it prevents cross-tenant data contamination, ensuring that a teacher at one school cannot accidentally access the records of another. This table is the bedrock of trust and compliance in the platform.
-- KPIs: Daily active users (DAU), user login success rate, account recovery frequency, multi-device login ratio, user retention rate.
-- Feature Reference: M01-F005, M01-F006, M01-F007, M17-F001

--Domain: School Management System (SMS) / Multi-Tenant SAAS ERP
-- database Object 4: auth.roles
-- database Object Type: Table
-- Description: The `roles` table defines the various functional personas and access levels available within the Halima Fathima Global School platform. It implements a robust Role-Based Access Control (RBAC) model by storing distinct role definitions such as Super Admin, System Admin, Teacher, Student, Parent, Accountant, and Librarian. Each role is scoped to a specific institute and branch, ensuring that role definitions can be customized or restricted per tenant. The table includes metadata like the role name, guard name for authentication context, and an optional description to clarify the role's intended purpose. By decoupling user identities from their permissions, this table allows administrators to dynamically assign and reassign access levels without altering the underlying permission matrix, providing a highly flexible and scalable security architecture that adapts to the complex hierarchical needs of modern educational institutions.
-- Business Case: The `roles` table is essential for maintaining strict operational security and workflow efficiency across diverse educational environments. In a school setting, a principal needs access to financial reports and staff management, while a teacher only needs access to their specific classes and grading tools. Without granular role definitions, the platform would either expose sensitive data to unauthorized users or become too restrictive to be functional. This table enables the SAAS provider to offer tiered feature access, where premium subscription plans might unlock advanced administrative roles or custom role creation capabilities. For the institution, it streamlines onboarding and offboarding; when a staff member changes departments, their role can be updated instantly, revoking old access and granting new access in a single action. This minimizes the risk of internal data breaches and ensures compliance with educational data privacy regulations.
-- KPIs: Role assignment coverage, custom role creation rate, role-based access violation attempts, average roles per user, role deprecation frequency.
-- Feature Reference: M01-F008, M01-F009, M16-F003

--Domain: School Management System (SMS) / Multi-Tenant SAAS ERP
-- database Object 5: auth.permissions
-- database Object Type: Table
-- Description: The `permissions` table catalogs every discrete action, route, and resource access point available within the Halima Fathima Global School platform. It works in tandem with the roles table to form a comprehensive RBAC system. Each record represents a specific capability, such as 'student_information.student_create', 'fees_management.smart_collection', or 'exam_module.mark_input'. The table stores the permission name, the guard name (typically 'web' or 'api'), and timestamps for tracking when permissions were introduced or modified. By maintaining a centralized registry of all possible system actions, this table allows developers and administrators to map out the exact security boundaries of the application. It ensures that every API endpoint and UI component can be protected by a specific permission check, preventing unauthorized access and providing a clear, auditable trail of what actions are permissible within the system's architecture.
-- Business Case: The business value of the `permissions` table lies in its ability to provide granular, audit-ready security and enable highly customized user experiences. For a CMMI Level 5 platform, traceability and strict access control are non-negotiable. This table ensures that sensitive operations, such as altering financial ledgers or modifying final exam grades, are restricted to only those explicitly authorized. From a product management perspective, it allows the SAAS provider to create specialized role templates for different types of institutions; for example, a university might require complex 'research_grant_management' permissions, while a K-12 school focuses on 'parent_communication' permissions. Furthermore, it simplifies compliance audits by providing a clear mapping of who can do what. If a data breach occurs, administrators can immediately identify which permission was exploited and revoke it across all affected roles, mitigating damage and ensuring regulatory compliance.
-- KPIs: Permission utilization rate, unauthorized access attempt frequency, permission audit completion rate, API endpoint protection coverage, role-permission mapping complexity.
-- Feature Reference: M01-F010, M01-F011, M16-F004

--Domain: School Management System (SMS) / Multi-Tenant SAAS ERP
-- database Object 6: auth.model_has_roles
-- database Object Type: Table
-- Description: The `model_has_roles` table serves as the critical polymorphic pivot table that links user entities to their assigned roles within the RBAC framework. Unlike traditional foreign key relationships, this table utilizes a polymorphic design, storing both the `model_type` (e.g., 'Modules\Authentication\Models\User') and the `model_id` to allow roles to be assigned to various entity types, not just users. This flexibility is essential for a CMMI Level 5 platform that may need to assign roles to future entity types like API clients or service accounts. The table ensures that a single user can hold multiple roles simultaneously, such as being both a 'Teacher' and a 'Class Teacher', enabling complex permission aggregation. By decoupling the user identity from role assignment, this table allows administrators to dynamically modify access levels without altering the core user records, providing a highly scalable and maintainable security architecture.
-- Business Case: The business necessity of the `model_has_roles` table stems from the complex, overlapping responsibilities inherent in educational institutions. A staff member might need to act as an 'Accountant' for fee collection but also as a 'Teacher' for classroom management. Without a polymorphic pivot table, the system would require rigid, mutually exclusive user types, severely limiting operational flexibility. This table enables the platform to support nuanced access scenarios, ensuring that users have exactly the permissions they need to perform their daily tasks without over-provisioning access. From a compliance standpoint, it provides a clear, auditable trail of who holds which roles, which is critical for internal security audits and regulatory compliance. Furthermore, the polymorphic nature of the table future-proofs the platform, allowing the SAAS provider to introduce new role-bearing entities (like automated bots or external integrations) without requiring a complete redesign of the authentication architecture.
-- KPIs: Multi-role assignment ratio, polymorphic entity support coverage, role reassignment frequency, access provisioning time, orphaned role assignment rate.
-- Feature Reference: M01-F012, M16-F005

--Domain: School Management System (SMS) / Multi-Tenant SAAS ERP
-- database Object 7: auth.model_has_permissions
-- database Object Type: Table
-- Description: The `model_has_permissions` table provides a direct, polymorphic mechanism to assign specific permissions to individual user entities, bypassing the standard role-based hierarchy when necessary. While the RBAC model typically assigns permissions to roles, which are then assigned to users, certain edge cases require granting a unique permission directly to a specific individual. This table stores the `permission_id`, `model_type`, and `model_id`, allowing for granular, user-specific access control. For example, a specific teacher might be granted the 'exam_module.modify_final_results' permission directly, even if their standard 'Teacher' role does not include it. This table works in conjunction with the role-based permissions to create a comprehensive, aggregated permission set for each user. It ensures that the platform can handle exceptional access requirements without compromising the overall security model, providing a flexible safety valve for complex administrative scenarios.
-- Business Case: The business value of the `model_has_permissions` table lies in its ability to handle exceptional access scenarios without disrupting the standardized role architecture. In large educational institutions, there are always edge cases where a specific individual needs temporary or permanent access to a sensitive function outside their normal job description. Without this table, administrators would be forced to create a custom role for a single user, cluttering the role registry and creating maintenance nightmares. This table allows for precise, surgical permission grants, ensuring that users have exactly the access they need for specific tasks. From an audit perspective, it provides a clear record of direct permission grants, allowing security teams to regularly review and revoke exceptional access to prevent privilege creep. This flexibility is crucial for maintaining operational agility while adhering to the principle of least privilege, a core requirement for CMMI Level 5 security standards.
-- KPIs: Direct permission grant frequency, privilege creep detection rate, exceptional access audit completion, permission aggregation latency, security policy violation rate.
-- Feature Reference: M01-F013, M16-F006

--Domain: School Management System (SMS) / Multi-Tenant SAAS ERP
-- database Object 8: auth.role_has_permissions
-- database Object Type: Table
-- Description: The `role_has_permissions` table is the fundamental pivot table that maps specific permissions to their corresponding roles within the RBAC framework. It consists of two primary foreign keys: `role_id` and `permission_id`. This many-to-many relationship ensures that when a role is assigned to a user, they automatically inherit all permissions associated with that role. The table is the backbone of the platform's access control logic, enabling administrators to define exactly what actions a 'Teacher', 'Accountant', or 'Librarian' can perform without having to assign permissions to each user individually. By centralizing the role-permission mapping, this table simplifies security management, allowing for bulk updates to access levels. If a new feature is added to the platform, developers can simply create the new permission and map it to the relevant roles in this table, instantly propagating the access rights to all users holding those roles.
-- Business Case: The `role_has_permissions` table is critical for scalable security management and operational efficiency. In an enterprise-level SAAS platform, manually assigning permissions to thousands of individual users is impossible and prone to error. This table enables the creation of standardized access templates (roles) that can be applied consistently across the organization. For the SAAS provider, it allows for the creation of tiered subscription models where higher-tier plans include access to advanced permissions (e.g., advanced analytics or API access). For the institution, it ensures consistency in security policies; when a job description changes, the administrator only needs to update the role's permissions in this table, and the changes are instantly reflected for all staff members in that role. This reduces administrative overhead, minimizes the risk of misconfigurations, and ensures that the platform remains secure and compliant as it scales.
-- KPIs: Role-permission mapping coverage, permission propagation latency, role configuration complexity, security policy update frequency, unauthorized role modification attempts.
-- Feature Reference: M01-F014, M16-F007

--Domain: School Management System (SMS) / Multi-Tenant SAAS ERP
-- database Object 9: auth.password_resets
-- database Object Type: Table
-- Description: The `password_resets` table is a legacy authentication support table used to manage the password recovery process for users who have forgotten their credentials. It stores a unique, time-sensitive token linked to the user's email address, along with a timestamp indicating when the token was created.
